# Personal Presence Baseline V1

Application-owned composition over Engine 0.4.0 / Arsenal 0.2.0 / Corps 0.1.0. No new package, CMS schema or Personal State domain.

`src/config/personal-presence.mjs` declares stable capability IDs, localized labels, paths, enabled flags, order, provider bindings, presentation profiles, reading eligibility and root membership. `src/features/personal-presence/model.mjs` validates and projects them. `src/lib/presence.ts` binds existing application configuration/content to the normalized contract; `presence-content.ts` resolves the canonical Author model and publications. The renderer never imports CMS/provider types.

The existing catch-all generates active public routes from this registry; global/root/local navigation, document profiles and sitemap use the same projection. Disabled or unpopulated capabilities produce no presence route/discovery entry. Audience explicitly adopts the pre-existing `newsletter` placeholder source through `legacyEntries`; disabling it prevents the generic content router from resurrecting that page without deleting its immutable source. Duplicate source ownership fails closed. Concrete route/namespace collisions and invalid data fail before generation; unknown provider binding never falls back silently. Existing `/about`, `/about/author`, `/about/contact`, `/about/support` remain instance defaults, not core invariants. The original authored About body stays immutable. A bounded remark projection maps its configured compatibility link identities to active routes (or non-link text when disabled), preserving labels/body source and preventing stale directory links after configuration changes.

Profile reuses the admitted About document. Author reuses existing Author identities; Contact uses explicitly public site configuration; Support reuses existing text and RSS. Resume, Portfolio, Campaign, Audience are architecture-ready, production-disabled/unpopulated. No fabricated biography, resume, project, provider, campaign or subscription. Campaign and Audience use the same bounded text/entries/links composition when truthful data is available, without a new runtime. Social and provider URLs remain configuration data.

Sections have stable IDs, text/entries/links type, localized label, enabled flag and numeric order. Entry lists support arbitrary count/ordering. The same renderer supports an explicit custom capability through a recognized provider/profile. Add fields/types only with a real use case. Profile/Author can use document commands including existing Super Share; Contact/Support do not acquire annotation/continuity eligibility. Tokens/preferences, Notch/Outline motion and dark contextual surfaces remain authoritative.

`node --test tools/presence/*.test.mjs` validates the strict/softcoded boundary. `node tools/presence/fixture-build.mjs` renders the exact production Astro component in an isolated temporary host with default/alternate branding, `/resume`→`/cv`, labels/order, portfolio disabled, provider/link replacement, section reorder and test-only Speaking. Synthetic files are removed and never enter production. Hosted feature and guarded release run desktop/touch tests plus all prior mandatory suites. No package extraction; first-consumer pressure is recorded only.
